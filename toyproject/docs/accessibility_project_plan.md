# 시각장애인 보행 접근성 지도 — 프로젝트 구상 및 데이터 조사 정리

> 작성 목적: 팀원 공유 + 개인 학습 정리. 아이디어 원문, 평가, 실제 조사한 데이터 현황, 실현 가능성 판단, 다음 단계를 시간 순서대로 정리한다.

---

## 1. 아이디어 원문 요약

중앙대 정문·후문 반경 약 1km 지역을 대상으로:

1. 그 지역의 인프라(상가, 병원 등)를 수집한다.
2. 가까운 인프라끼리 짝을 지어 **"구간"** 을 정의한다.
3. 각 구간(양 끝 인프라 사이)에 대해 **시각장애인 편의시설, 경사도** 등의 데이터를 종합해 **난이도/험준도 지표**를 만든다.
4. 이를 지도화해서 **대시보드**로 만든다.

기존에 진행 중이던 `MAP_Project`(Yelp 리뷰 기반 커플 장소 예측 + 카카오 API 한국 장소 수집, `analysis_process.md` 참고)의 데이터 수집 인프라를 재사용하되, 주제를 시각장애인 보행 접근성으로 전환하는 방향.

---

## 2. 아이디어 평가

**강점**
- 정문/후문 2곳, 반경 1km로 범위가 작고 명확함 → 파일럿 프로젝트로 적합 (서울 전체 수집은 이미 수 시간 걸리는 것을 확인한 바 있음).
- "인프라 노드 → 인접 쌍 → 구간(edge) → 구간별 난이도 스코어"는 보행 네트워크 분석에서 실제로 쓰이는 그래프 모델이라 구조 자체가 타당함.
- 사회적 의미가 있는 주제.

**핵심 리스크 (착수 전 확인이 필요했던 것들)**
1. 경사도 데이터가 실제로 존재하는가
2. 시각장애인 편의시설(점자블록 등) 데이터가 실제로 존재하는가, 특히 동작구/중앙대 지역에
3. "짝짓기"를 직선거리로 할지, 실제 보행자 도로망에 스냅해서 할지 — 직선으로 이으면 실제 걷는 경로와 무관한 구간이 생겨서 경사도를 매기는 것 자체가 무의미해짐. **보행자 도로망 데이터 확보 여부가 프로젝트 성패를 가르는 선결 조건**이라고 판단.

## 3. 데이터 조사 결과

### 3-1. 정부/공공 데이터 (공공데이터포털, 서울 열린데이터광장)

| 필요 데이터 | 존재 여부 | 출처 | 비고 |
|---|---|---|---|
| 경사도 | △ 있음 (가공 필요) | [서울특별시_경사도](https://www.data.go.kr/data/15100676/fileData.do) / [서울 열린데이터광장](https://data.seoul.go.kr/dataList/OA-22241/F/1/datasetView.do) | 경사도 수치가 아니라 **등고선·표고점 SHP**(국토지리정보원 2023 수치지형도 기반, 서울 전역, zip 101MB) 제공 → 직접 보간해서 구간별 경사도를 계산해야 함. 갱신주기 없음(1회성) |
| 보도(인도) 상세정보 | △ 있음 (컬럼 확인 필요) | [서울시 보도통계자료](https://data.seoul.go.kr/dataList/OA-22240/F/1/datasetView.do) | 노선별 방향·위치·폭·면적·**보도블록 종류**·투수여부·시공연도, 연 1회 갱신, 자치구 필터 가능. "보도블록 종류"가 점자블록까지 포함하는지는 실제 다운로드해서 확인 필요 (형식: Excel) |
| 장애인 편의시설 | △ 있음 (성격 다름) | [한국사회보장정보원 장애인편의시설현황 API](https://www.data.go.kr/data/15092317/openapi.do) | 경사로·승강기·점자블록 정보 제공하지만 **건물(시설) 단위** 데이터라 도로 위 점자블록과는 다름. 주소 기반이라 좌표는 별도 지오코딩 필요할 가능성 |

**참고**: 서울시/국토지리정보원 데이터는 보통 중부원점 TM 좌표계(EPSG:5186)를 쓰므로, 카카오 API(WGS84) 좌표와 합치려면 `pyproj`로 좌표계 변환이 필요함.

### 3-2. OpenStreetMap(OSM) — 실측 확인 완료

Overpass API가 계속 타임아웃되어(서버 과부하로 추정), OSM 원본 API(`api.openstreetmap.org/api/0.6/map`)로 **직접 데이터를 받아 실측**함.

**좌표 확인**
- 중앙대 정문 (OSM 태깅된 실제 노드): **37.5070419, 126.9591522**
- 서울캠퍼스 전체 bounding box: 위도 37.5018~37.5070, 경도 126.9539~126.9596 (약 500~600m 범위)
- 후문은 OSM에 명칭으로 태깅되어 있지 않음 → 좌표 별도 확정 필요. 다만 캠퍼스 자체가 좁아 정문 기준 반경 1km면 캠퍼스 전체와 양쪽 출입구 주변을 대부분 포함함.

**정문 반경 1km(2.2km×2.2km bbox) 내 실측 결과**

| 항목 | 개수 | 판단 |
|---|---|---|
| 전체 way | 1,811 | 도로망 자체는 충분히 조밀 |
| 도보 관련 way (footway 65 + pedestrian 23 + path 20 + crossing 20 + steps 37) | **165개** | 보행자 네트워크가 실제로 매핑되어 있음 → 직선 근사가 아니라 **실제 도로망 스냅 방식이 가능** |
| `tactile_paving`(점자블록) 태그 | **31개** | 대부분 횡단보도(crossing) 노드에 붙어있음. 완전하진 않지만 시작 데이터로 활용 가능 |
| `wheelchair` 태그 | 15개 | 보조 데이터 |
| `sidewalk`(인도 유무) 태그 | 15개 | 보조 데이터 |
| `kerb`(연석 경사 타입) 태그 | **0개** | 연석/턱낮춤 상세 정보는 OSM에 없음 — 명확한 한계 |
| `incline`(경사도) 태그 | 7개 | 거의 없음 → 3-1의 서울시 경사도(등고선) 데이터로 직접 계산해야 함 |

전체 node 수: 16,086개.

## 4. 실현 가능성 판단: **진행 가능 (Go)**

가장 큰 리스크였던 "보행자 도로망 자체가 존재하는가"가 실측으로 확인됐고(165개 도보 관련 way), 점자블록·휠체어 접근성도 일부 크라우드매핑되어 있음. OSM 좌표계가 WGS84라 카카오 API 좌표와 바로 합칠 수 있어 좌표계 변환 문제도 이 경로에서는 발생하지 않음.

**남는 한계 (MVP 설계 시 반영 필요)**
- 연석/턱낮춤(kerb) 정보는 OSM에 전무 → 이 항목은 점수 체계에서 제외하거나, 서울시 보도통계자료로 보강하거나, 직접 현장조사가 필요함.
- 경사도는 OSM만으로 부족 → 서울시 경사도(등고선 SHP) 데이터를 따로 계산해서 결합해야 함 (여전히 가공 작업 남음).
- 점자블록 태그(31개)가 크라우드소싱 데이터라 완전성이 보장되지 않음 (매핑 안 된 실제 점자블록이 있을 수 있음).

## 5. 다음 단계 (제안 순서)

1. **정문/후문 정확한 좌표 확정** — 후문은 OSM에 이름 태깅이 없어 지도에서 직접 좌표를 따야 함.
2. **인프라(POI) 수집** — 기존 `collect_kakao_places.py` 재사용, 카테고리만 상가/병원/약국 등으로 재설정.
3. **보행자 도로망 그래프화** — `osmnx` 같은 라이브러리로 이 bbox의 도보망(way+node)을 불러와 그래프 구성, 카카오 인프라 좌표를 가장 가까운 도로망 노드에 스냅.
4. **경사도 결합** — 서울시 경사도(등고선) 데이터를 받아 도보망 각 구간에 매칭 계산.
5. **접근성 데이터 결합** — OSM `tactile_paving`/`wheelchair` 태그를 우선 반영하고, 부족한 부분은 서울시 보도통계자료·장애인편의시설 API로 보강.
6. **구간 난이도 지표 설계** — MVP는 경사도 + 접근성 태그 유무의 단순 가중합으로 시작.
7. **지도 시각화/대시보드** — Folium 또는 Streamlit.
